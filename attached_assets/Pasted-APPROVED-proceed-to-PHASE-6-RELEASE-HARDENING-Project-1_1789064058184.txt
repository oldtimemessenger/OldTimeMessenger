PHASE 6A — DEFINE THE MONEY MODEL

There must be a strict distinction between:

1. Purchased Coins
2. Creator Gold / earnings
3. Withdrawable creator balance
4. Real-money payouts

Do not allow UI wording to imply that purchased Coins are directly withdrawable.

Review and correct the existing wording around:

* 90 Coins = $1
* 90 Gold = $1

Determine exactly what each balance represents.

The server must remain authoritative for all monetary/virtual-currency calculations.

Do not trust client-provided balances, prices, conversion rates, or payout amounts.

PHASE 6B — IMMUTABLE LEDGER

Audit the existing balance-changing operations:

* Coin purchases
* Coin spending
* Gifts
* Gold/creator earnings
* Refunds
* Reversals
* Withdrawals
* Payout completion/failure

If a durable immutable ledger does not currently exist, implement one using the existing database architecture.

Requirements:

* Every balance-changing transaction gets a unique idempotency key.
* Repeated requests must not double-credit or double-debit.
* Ledger entries must be auditable.
* Balance changes must be transactional.
* Client retries must be safe.
* Failed operations must not partially modify balances.
* Server calculates all monetary values.
* Never allow negative balances unless explicitly supported by a documented business rule.

Do not simply add another client-side balance field.

PHASE 6C — REVENUECAT

Review:

* mobile/lib/revenuecat.tsx
* lib/revenuecat.ts
* RevenueCat provider
* server purchase verification
* wallet credit flow

Verify the intended flow:

Apple/Google purchase
→ RevenueCat
→ transaction verification
→ server
→ idempotent purchase record
→ wallet credit

Requirements:

* Valid purchases credit exactly once.
* Duplicate transaction delivery does not credit twice.
* Restore purchases does not duplicate credits.
* Invalid purchases are rejected.
* Missing RevenueCat configuration fails clearly.
* Missing offerings do not silently look like “no products available.”
* Product IDs are explicitly mapped to known coin packs.
* Client cannot choose an arbitrary credit amount.
* Server must determine the amount of Coins granted for each product.

If the existing architecture already has server-side RevenueCat verification, preserve it and strengthen it rather than replacing it.

PHASE 6E — CREATOR GOLD / EARNINGS

Separate creator earnings from purchased Coins.

Do not use floating-point arithmetic for monetary settlement.

Use integer minor units or another deterministic representation for real-money values.

Document:

* Coin purchase value
* Coin spend value
* Gold earned from gifts
* creator/platform split
* withdrawable amount
* minimum withdrawal if one exists

If any of these rules are not currently finalized in the codebase, do not invent business terms silently. Identify them as product decisions required before launch.
